# Мониторинг сервиса рекомендаций

## Архитектура

```
клиент -> app (FastAPI, :8000) --/metrics--> Prometheus (:9090) --> Grafana (:3000)
                |
                v
          Postgres (витрина фичей)
```

Метрики отправляются **из кода проекта**: `service/monitoring.py` объявляет
счётчики и гистограммы, middleware замеряет каждый HTTP-запрос, эндпоинты
учитывают выдачу. Prometheus скрейпит `GET /metrics` сервиса раз в 5 секунд,
Grafana читает Prometheus. Дашборд и datasource заводятся автоматически через
provisioning — после `docker compose up` ничего настраивать руками не нужно.

## Запуск

```bash
python -m scripts.export_model      # выгрузить модель из MLflow Registry в models/
docker compose up -d --build
```

- сервис: http://localhost:8000 (Swagger: /docs)
- Prometheus: http://localhost:9090
- Grafana: http://localhost:3000 — дашборд «bank_recsys service» (анонимный вход включён)

## Метрики из кода сервиса

| метрика | тип | лейблы | что показывает |
|---|---|---|---|
| `http_request_duration_seconds` | Histogram | `method`, `handler`, `status` | Время обработки каждого HTTP-запроса от получения до ответа. `handler` — шаблон пути (`/recommend/{ncodpers}`), а не конкретный URL, чтобы кардинальность не росла с числом клиентов. Из неё же считается RPS (`rate(..._count)`) и доля ошибок (по лейблу `status`). |
| `prediction_seconds` | Histogram | — | Чистое время скоринга кандидатов CatBoost-моделью, без похода в Postgres и HTTP-слоя. Позволяет отличить «тормозит база» от «тормозит модель». |
| `recommendations_total` | Counter | `product`, `source` | Сколько раз продукт попал в выдачу top-7. База для панели «самые частые рекомендации» и для контроля деградации: если распределение резко перекосило в один продукт — модель или данные сломались. |
| `recommend_requests_total` | Counter | `source` | Запросы по источнику выдачи: `model` — персональное ранжирование, `popular` — холодный старт (клиента нет в витрине). Рост доли `popular` означает, что витрина отстаёт от притока клиентов. |
| `client_staleness_months` | Histogram | — | На сколько месяцев устарел снапшот клиента в витрине на момент запроса. Рост среднего — сигнал, что витрина давно не перезаливалась. |

Плюс стандартные коллекторы `prometheus_client`: `process_cpu_seconds_total`
(CPU процесса), `process_resident_memory_bytes` (память RSS),
`python_gc_*` — они дают панели CPU и памяти без дополнительного кода.

## Панели дашборда

| панель | запрос (суть) | зачем смотреть |
|---|---|---|
| CPU процесса | `rate(process_cpu_seconds_total[1m])` | Нагрузка сервиса; рост без роста RPS — утечка/деградация |
| Время обработки p50/p95/p99 | `histogram_quantile(...)` по `/recommend.*` | SLO по латентности; p99 ловит хвост от медленной базы |
| RPS по эндпоинтам и статусам | `rate(http_request_duration_seconds_count[1m])` | Трафик и всплески ошибок в одном месте |
| Самые частые рекомендации | `topk(10, increase(recommendations_total[range]))` | Дрейф выдачи: перекос в один продукт = проблема модели/данных |
| Модель vs холодный старт | `increase(recommend_requests_total[range])` по `source` | Доля клиентов без персонализации |
| Чистый инференс p95 | `histogram_quantile(0.95, prediction_seconds)` | Отделяет время модели от времени базы |
| Память RSS | `process_resident_memory_bytes` | Утечки; модель+бандл держатся в памяти постоянно |
| Средняя устарелость снапшота | `client_staleness_months_sum / _count` | Свежесть витрины |
| Доля ошибок | не-2xx / все запросы | Здоровье сервиса одним числом |

## Пороговые значения (ориентиры для алертов)

- p95 `http_request_duration_seconds` > 1 с в течение 5 минут — деградация (норма ~0.15-0.25 с);
- доля не-2xx > 1% — ошибки;
- доля `source="popular"` > 20% — витрина отстаёт от притока клиентов;
- средняя `client_staleness_months` > 1 — витрина не обновлялась после свежей выгрузки.

Алерты сознательно не заведены в этом стенде (нет канала доставки), но все
пороги выражаются одним PromQL-выражением поверх уже собираемых метрик.
