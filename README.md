# bank_recsys — рекомендации банковских продуктов

Сервис предсказывает, какие банковские продукты предложить клиенту: для
каждого клиента ранжирует продукты, которых у него ещё нет, по вероятности
покупки в следующем месяце и отдаёт top-7 по HTTP API.

Данные — Santander Product Recommendation: 13.6 млн записей, 956 645
клиентов, 17 месяцев (2015-01 — 2016-05), 24 продукта.

## Структура проекта

```
data/                    сырой csv + подготовленный parquet (не в git)
notebooks/EDA.ipynb      разведочный анализ, выводы о данных
notebooks/Experiments.ipynb  эксперименты с моделями, логирование в MLflow
scripts/
  preprocessing.py       чистка сырых данных, таргет (CLI: -m scripts.preprocessing)
  features.py            снапшоты, кандидаты, лаговые фичи, affinity-статистики
  metrics.py             MAP@K
  train.py               обучение/инференс CatBoost
  artifacts.py           бандл артефактов фичей (pop_rate, affinity, ...)
  serving_store.py       витрина фичей в Postgres
  build_serving_table.py заливка витрины (CLI)
  export_model.py        выгрузка модели из MLflow Registry (CLI)
service/                 FastAPI-сервис: app, recommender, monitoring, logging
monitoring/              конфиги Prometheus и Grafana (dashboard as code)
run_mlflow.sh            запуск MLflow-сервера (Postgres + S3)
Dockerfile, docker-compose.yml
Monitoring.md            описание метрик мониторинга
requirements.txt         полное окружение экспериментов (pip freeze)
```

## Бизнес-задача и метрики

**На что влияем.** Выдача релевантных продуктов повышает конверсию
предложения в покупку и доход на клиента; нерелевантная выдача выжигает
канал коммуникации. Прокси этих бизнес-метрик в офлайне — качество
ранжирования top-7.

**Основная ML-метрика: MAP@7.**

Целевое событие — переход владения продуктом из 0 в 1 между соседними
месяцами. Задача ранжирующая: важно не точное значение вероятности, а позиция
реально купленного продукта в выдаче. MAP@7 учитывает порядок рекомендаций
(первая позиция ценнее седьмой) и корректно обрабатывает несколько покупок за
месяц. Отсечка 7 соответствует каталогу (22 продукта в обучении) и разумному
объёму выдачи в интерфейсе.

По данным EDA среднее число покупок на событие равно 1.26 — почти всегда
покупается один продукт, и MAP@7 вырождается в MRR@7: качество определяется
тем, насколько высоко модель поднимает единственный верный продукт.

**Почему не альтернативы.** Accuracy и F1 неинформативны при доле позитивов
3.27%: модель, всегда предсказывающая отсутствие покупки, даёт свыше 96%
accuracy. ROC-AUC оценивает продукты по отдельности и не отвечает на вопрос,
какие семь показать конкретному клиенту (это подтвердилось экспериментально:
AUC 0.92 сочетался с MAP@7 хуже baseline). Precision@7 и Recall@7 игнорируют
порядок внутри выдачи. NDCG@7 при бинарной релевантности не даёт ничего сверх
MAP.

**Онлайн-метрики сервиса** (Prometheus, см. [Monitoring.md](Monitoring.md)):
латентность, доля ошибок, доля холодного старта, устарелость витрины,
распределение рекомендаций по продуктам.

## Обработка данных

`scripts/preprocessing.py` (код идентичен EDA, сверен поколоночно):

- удалены `conyuemp` (99.99% пропусков), `ult_fec_cli_1t` (99.8%), `tipodom`
  (константа);
- числовые поля, приходящие строками (`age`, `antiguedad`, `indrel_1mes`),
  приведены к числам; заглушка `-999999` в `antiguedad` заменена на NaN;
- пропуски не импутируются на этапе подготовки — статистики считаются внутри
  пайплайна на train во избежание утечки;
- таргет `*_buy`: продукт куплен в месяце M, если владение 0 в M-1 и 1 в M;
  первые месяцы клиентов без валидного M-1 исключаются из обучения.

**Обучающий формат** (`scripts/features.py`): long-таблица «один кандидат —
одна строка» `(клиент, месяц, продукт) -> label`, кандидаты — только
продукты, которых не было в M-1. Все динамические признаки берутся из
предыдущего месяца (лаговая форма — активность может меняться одновременно с
покупкой). Два признака уровня «клиент-продукт»: `product_pop_rate` (частота
покупки продукта среди валидных кандидатов) и `affinity_score`
(P(купит j | владеет i), усреднённая по продуктам клиента) — считаются только
по train.

## Модель и эксперименты

Единая бинарная модель CatBoost на всех продуктах (`product` — категориальный
признак), обучение на 8 последних месяцах, валидация строго временная — на
последнем месяце (2016-05). Негативы прорежены равномерно по продуктам
(6% негативов), вес позитивного класса — корень из натурального соотношения
классов с поправкой на сэмплирование.

| эксперимент | MAP@7 на 2016-05 |
|---|---|
| baseline: top-7 по популярности | 0.01935 |
| CatBoost, per-product сэмплинг 15:1 | 0.01223 |
| + фичи affinity_score / product_pop_rate | 0.01760 |
| + равномерный сэмплинг, 8 свежих месяцев, sqrt-веса | **0.02496** |

Итог: **+29% к baseline**.

Два принципиальных урока (подробности в `Experiments.ipynb`):

1. **Сэмплирование негативов внутри продукта уничтожает приор продукта.**
   Натуральная частота покупки различается между продуктами в 3082 раза;
   фиксированное соотношение neg:pos на продукт делало её одинаковой у всех —
   модель при высоком AUC (0.92) проигрывала baseline по MAP@7. Равномерная
   доля негативов по всем продуктам сохраняет приоры точно.
2. **Ранняя остановка по AUC вредна**: AUC растёт там, где MAP@7 падает.
   Число деревьев подбирается по MAP@7 на срезах `ntree_end` без переобучения
   (оптимум — 300 из 600).

Финальная модель зарегистрирована в MLflow Model Registry: `bank_recsys`,
алиас `champion`, обрезана до 300 деревьев. Вместе с моделью версионируется
бандл артефактов фичей (`pop_rate`, `affinity`, порядок колонок) — без него
фичи в проде невоспроизводимы.

## Архитектура сервиса

```
клиент -> FastAPI (:8000) -> Postgres (витрина фичей, 1 строка на клиента)
             |                    ^
             v                    | scripts/build_serving_table.py
        CatBoost (300 деревьев,   |
        локальный model.cb)    data/interim (после preprocessing)
```

- `GET /recommend/{ncodpers}` — топ-7 для клиента. Известный клиент:
  кандидаты строятся тем же кодом, что на обучении, скорятся моделью
  (`source: "model"`, поле `stale_months` — свежесть снапшота). Неизвестный:
  фолбэк на топ популярных (`source: "popular"`).
- `GET /recommend/popular` — топ-7 популярных явно (холодный старт).
- `GET /health` — модель загружена, витрина отвечает.
- `GET /metrics` — метрики Prometheus (см. [Monitoring.md](Monitoring.md)).
- Swagger: `/docs`.

Модель и бандл вшиваются в Docker-образ на этапе сборки; в рантайме сервис
зависит только от Postgres. Латентность ~130-200 мс на запрос (почти целиком
поход в облачный Postgres; чистый инференс ~5 мс).

## Запуск с нуля

Предусловия: заполненный `.env` в корне (`DB_DESTINATION_*` — Postgres,
`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`S3_BUCKET_NAME` — S3); Docker;
сырой файл `data/train_ver2.csv.zip`.

```bash
# 0. Окружение
python3.10 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 1. Данные: сырой csv -> data/interim (parquet + meta.json), ~5 мин
python -m scripts.preprocessing

# 2. MLflow-сервер (Postgres backend + S3 artifacts).
#    nohup, а не просто `&`: иначе сервер умрёт вместе с закрытым терминалом
nohup bash run_mlflow.sh > mlflow.log 2>&1 &

# 3. Витрина фичей в Postgres (последний снапшот каждого клиента), ~1 мин
python -m scripts.build_serving_table

# 4. Обучение: notebooks/Experiments.ipynb — эксперименты, логирование в
#    MLflow, регистрация лучшей модели в Registry (alias `champion`).
#    Обязателен при первом запуске на пустом Registry: шаг 5 берёт модель
#    оттуда и без неё упадёт с "Registered Model not found". Если модель уже
#    зарегистрирована, шаг нужен только для переобучения.

# 5. Выгрузка production-модели из Registry в models/
python -m scripts.export_model

# 6. Сервис + мониторинг
docker compose up -d --build

# 7. Проверка
curl http://localhost:8000/health
curl http://localhost:8000/recommend/15889
```

Интерфейсы: сервис http://localhost:8000 (Swagger `/docs`), MLflow
http://localhost:5000, Prometheus http://localhost:9090, Grafana
http://localhost:3000 (дашборд «bank_recsys service», анонимный вход).

Проверено: полный прогон шагов 1-7 с остановленных сервисов и удалённого
`models/` воспроизводит скоринг до последнего знака.

## Сопровождение

- **Свежая выгрузка данных**: `python -m scripts.preprocessing` →
  `python -m scripts.build_serving_table`. Сервис подхватывает витрину без
  рестарта (читает Postgres на каждый запрос).
- **Переобучение**: `Experiments.ipynb` → регистрация в Registry → перевесить
  алиас `champion` → `python -m scripts.export_model` →
  `docker compose up -d --build app`.
- **Мониторинг и пороги алертов**: [Monitoring.md](Monitoring.md). Ключевые
  сигналы деградации: рост доли `source="popular"` (витрина отстаёт от притока
  клиентов), рост `client_staleness_months` (витрина не обновлялась), перекос
  распределения `recommendations_total` в один продукт.
- **Логи**: единый формат в stdout (`docker logs bank_recsys_app`), уровень —
  переменная `LOG_LEVEL`. Каждый запрос рекомендаций логируется с исходом
  (source, stale, топ-продукт).

## Воспроизводимость

- Единственный источник случайности — `random_state` в
  `data/interim/meta.json` (сэмплирование негативов, подвыборки, seed
  CatBoost).
- `requirements.txt` — полный срез окружения экспериментов;
  `service/requirements.txt` — минимальные зависимости сервиса (совпадающие
  версии).
- Эксперименты, параметры и метрики — в MLflow (эксперимент `bank_recsys`);
  модель и бандл фичей версионируются вместе в Model Registry.
